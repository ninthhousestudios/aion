# Release Review Synthesis — aion @ all-of-HEAD (`e883a4e`)

**Date:** 2026-05-31 · **Scope:** all of HEAD on `main` (32 commits, first review) · **Type:** release gate

**Verdict: HOLD for fixes.** One Critical contract violation that loses data, a red regression net
on the most-churned subsystem, and an already-shipped contract drift that breaks the one renderer
just wired up. None are large; all should land before a release tag.

This synthesis is the entry point. The two source passes are appendices:
- Code review (correctness, contracts, slop): [`2026-05-31-all-HEAD-review.md`](./2026-05-31-all-HEAD-review.md) — 9 findings (1 Critical, 2 High, 4 Medium, 2 Low)
- Architecture deepening (structural friction): [`2026-05-31-all-HEAD-architecture.md`](./2026-05-31-all-HEAD-architecture.md) — 5 candidates + 2 ADR notes

The design itself is sound. The three-layer model (Canvas geometry → Card bindings → Workspace/Chart
store → MCP plugins) holds, and the "core has zero astrological knowledge" contract genuinely survives
in `lib/` — domain data flows as opaque payloads through `PluginHost`, and nothing in the canvas knows
what a planet is. The problems are not in the shape of the architecture; they are in **contracts that
were implemented as copies instead of owned**, and a **storage layer built more strictly than the
domain model allows**.

## Convergent root causes (highest leverage — both passes hit these)

### A. Contracts implemented as copies, not owned — and three of them have already drifted

This is the dominant theme, and both passes hit it from different angles. The disease: a contract
(a data shape, a hash scheme, a mapping) is re-implemented at each consumer instead of owned by one
module. Nothing forces the copies to agree, so they silently diverge. **It has already happened in
three independent places:**

1. **The Expression JSON shape** (architecture #1 — *review missed this; direction corrected by
   orchestrator verification against drishti source*). Two consumers re-parse drishti's
   `calculate_chart` output with their own private key sets. **Verified:** drishti emits planets keyed
   `retrograde`/`house` and houses keyed `cusp_longitude` (`drishti/.../chart_formatter.dart`) — so the
   **South Indian Renderer is correct**, and **`vector_extractor` is the divergent one** (it reads
   `is_retrograde`/`house_number`/house-`longitude`, which drishti does not emit; its `ascmc` reads do
   match). This is **latent**, not live: `extractVector`'s only caller, `ChartService.createChart`, is
   wired to nothing (`import_charts` inserts via `ChartRepository.insert` directly), so it bites when
   similarity-search is wired to real drishti output. `vector_extractor_test` is green only because its
   fixture is self-consistently wrong. **Medium**, and the fix target is the extractor + its fixture —
   not the renderer.
2. **The config hash** (review `config-id-not-canonicalized` + `config-hash-two-schemes`). The app
   canonicalizes (sort keys) then treats the sorted JSON string as the "hash"; `create_config`
   sha256s the *raw* preset string. Two incompatible schemes both called "the config hash" —
   idempotency that isn't, and a guaranteed cache-miss the moment anything correlates an
   `ExpressionRef` with a persisted `Config`.
3. **The ChartData→Chart import mapping** (review `duplicate-store-and-importer`). `lib/import/ChartImporter`
   (tested, unwired) and `import_charts._importFile` (wired, untested) implement the same mapping
   independently; the wired one hand-rolls it. Plus `WorkspaceStore` is a line-for-line dead duplicate
   of `ChartStore`'s decode path, kept green only by its own test.

**Why it's the highest-leverage cluster:** the fixes are mostly *deletion and consolidation*, and each
removes a whole class of future drift. Own the Expression shape in one typed parse-once module (arch #1);
define one canonical-hash helper used on both sides (the app already has the logic — review §Synthesis);
delete the unwired twins (`WorkspaceStore`, `ChartImporter`). Pin a correctness fix for the renderer
keys *now*; the typed boundary is the deepening that stops it recurring.

### B. The MCP tool boundary is untested and internally duplicated

Both passes independently flag `packages/chart_db/lib/src/tools/*` (review `chartdb-mcp-server-untested`,
architecture #3). This is the contract boundary between core and plugins — where CONTEXT.md's glossary
becomes wire keys — and it has **zero tests** while the engine beneath has 172. It also carries the same
copy-paste disease as cluster A: `_errorResult` duplicated across 5+ files, and two `Chart→Map`
serializers (`get_chart` emits nulls, `search_charts` omits them) that already disagree. Untyped
`args['weights'] as Map` casts throw into a generic catch.

The fix serves both passes at once: factor the shared `_errorResult` + `try→CallToolResult` wrapper +
one canonical `Chart→Map` serializer, then make each `_handle` a plain function tested directly against
an in-memory `ChartDatabase` (no stdio needed). Cheap, given the engine's existing coverage.

## Single-pass findings that still block or matter

These didn't converge but two of them are the actual release blockers:

- **CRITICAL — `charts UNIQUE(jd,lat,lon)` contradicts the natural-key invariant** (review). CONTEXT.md
  says the natural key is a *dedup hint, not hard uniqueness* — twins and unrelated same-JD events may
  legitimately share it. The schema makes that impossible (`database.dart:76`); the import path silently
  swallows the second Chart as a duplicate. **Data loss against an explicitly-allowed case.** This is the
  one Critical and it gates any release that imports real data.
- **HIGH — red canvas regression net** (review). 6 stale `test/canvas/*` tests assert pre-`10958e1`
  defaults. A red suite is an off suite: a real regression in `WorkspaceNotifier` (the highest-churn app
  area) would go uncaught. Cheap to fix; do it *before* deleting the duplicate twins so the deletions are
  covered.
- **Architecture-only deepenings** (#4, #5): the Chart→Expression→Card binding is smeared across a UI
  context-menu handler with hardcoded `'drishti'`/`'calculate_chart'`/`'south_indian'` literals; the
  Renderer registry is a one-adapter import-time global living in a UI file. Neither blocks release —
  these are HITL deepening candidates that need design grilling before implementation.

## ADRs worth recording (none exist yet)

1. drishti's `calculate_chart` output is the canonical Expression schema, owned/parsed by exactly one
   module. (The unrecorded version of this invariant is what let the renderer/extractor keys diverge.)
2. MCP tool handlers are tested as plain functions against the in-memory engine, not over stdio.
3. (Implicit in Wave A) the storage model: TOML source-of-truth vs sqlite-derived, and natural-key-as-hint.

## Note on pack accuracy

The code-intel pack cleared all `lib/` code of dead-code concerns; the review corrected this — the
unwired-but-tested twins (`WorkspaceStore`, its providers, `ChartImporter`) are real production slop
that `sutra_dead` can't see because a `*_test.dart` import counts as a use. Pack-build filter should
treat "imported only by `*_test.dart`, never from the runtime entrypoint" as a dead-code *candidate*
rather than auto-clearing it.
